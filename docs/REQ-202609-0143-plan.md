# 中国区首页数据随机 — 技术方案

需求编号：REQ-202609-0143
分支：`req-202609-0143`

## 一、需求复述

大陆数据量最大（审核通过 46,908 条），但首页永远按 `created_at` 倒序返回最新的一批 —— 每次打开、每次刷新看到的都是同一批面孔，其余案件从来没有曝光机会。要求：**只要访客没有特地选择地区，每次刷新首页都应随机返回不同的数据**，让更多没曝光过的记录得到曝光机会。

## 二、现状

`src/app/api/cases/route.ts` 的 CN 分支固定 `.orderBy(desc(schema.cases.createdAt))`，首页 `src/app/page.tsx` 的请求参数里只有 page / limit / countryCode / 地区 / 性别 / 搜索，没有任何随机因子。项目里已有的 `/api/cases/random` 端点用的是 `ORDER BY RANDOM()`，只被别处用到，首页没走。

## 三、设计

### 3.1 分页与随机的矛盾：不能用 `ORDER BY RANDOM()`

首页是「加载更多」式分页（每页 24 条，`page` + `limit` 走 `OFFSET`）。`ORDER BY RANDOM()` 每次请求重新掷骰子，第 2 页会重复第 1 页的部分记录、同时漏掉另一些，页面越翻越乱。实测里这正是必须回避的失败模式。

### 3.2 用「种子 + md5」得到稳定的随机全序

```sql
ORDER BY md5($seed || id)
```

- 对固定的 seed 而言，排序键是 `(seed, id)` 的纯函数 → **同一个种子反复请求顺序完全一致**，分页不重不漏（实测 5 页 120 条去重后仍是 120）。
- seed 随每次页面加载变化 → 每次刷新的首屏是另一批数据。
- `md5` 的输出在 `[0, 2^128)` 上均匀分布，就是一列近似真随机的排序键；`md5($1 || id)` 是普通表达式，Postgres 走 full scan + sort，没有索引也够快（46,908 行，第 1 页 109ms、第 101 页 88ms，线上原有查询同样是全表 count）。

### 3.3 seed 的生成与生命周期

- **前端生成**：`useState(() => Math.random().toString(36).slice(2, 10))` —— 每次页面加载（含刷新）一个新种子。
- **必须固定在 state 里，不能每次请求现生成**：分页要求同一个种子，否则「加载更多」会翻到另一套顺序上。实测里第三次点「加载更多」时三个请求的 seed 完全一致。
- **由请求带上**：首页在 `/api/cases` 的 query 上恒定带 `seed=...`。seed 变化同时天然击穿任何一层 URL 缓存。

### 3.4 服务端：白名单校验 + 只在「没选地区」时打乱

- seed 虽然走绑定参数（不存在注入），但排序键里会拼接这个字符串 —— 不设限的话调用方可以塞进上兆文本让排序变慢。因此白名单校验 `/^[a-z0-9]{1,32}$/i`，不合规就当作没传。
- **只有 CN 分支**（需求标题就是中国区；首页默认 `countryCode=CN`）。非 CN 走动态表 + `pool.query` 的既有时序路径，本次不动。
- **只有没选省 / 市 / 区时**才打乱。选了地区说明访客在找特定的人，「随机」反而妨碍按时间排查；这也正对应需求里的「只要我没有特地选择地区」。性别、姓名搜索不影响是否打乱（姓名搜索本身就是定向查找，但打乱与否对单页结果无实质影响，保持逻辑简单）。

## 四、改动清单

- `src/app/api/cases/route.ts`
  - 新增 `SEED_PATTERN` 白名单与 `shuffledOrder(seed)`（`sql\`md5(${seed} || ${schema.cases.id})\``）。
  - 解析 `?seed=`，非法值降级为 `null`。
  - CN 分支的 `orderBy` 改为：`seed && !province && !city && !district ? shuffledOrder(seed) : desc(createdAt)`。
- `src/app/page.tsx`
  - 新增 `const [seed] = useState(() => Math.random().toString(36).slice(2, 10))`。
  - `fetchCases` 恒定带上 `params.set("seed", seed)`，`seed` 进 `useCallback` 依赖数组。
- `README.md`：首页小节补一句随机排序的说明。

## 五、验收标准

1. 不选地区时，连续刷新首页首屏是不同批次的数据（重合接近 0）。
2. 同一个 seed 反复请求，顺序稳定；连续翻页不重复、不漏记录。
3. 选了省份后列表恢复按时间倒序（不被打乱）。
4. 不带 seed 或 seed 非法时，行为与改动前完全一致（时间倒序）。
5. `tsc --noEmit` 通过；`npm run lint` 不新增问题（基线 86 errors / 30 warnings）；`next build` 通过。

## 六、验证结果

本地起 worktree 构建产物于 `http://localhost:3100` 实测（CN，46,908 条）：

| 断言 | 结果 |
| --- | --- |
| 5 个随机 seed 的首屏 6 条 | 互不相同（`2bd4f69a…` / `4098e97a…` / `ded68b1e…` / `632c8c94…` / `f23ac3b2…`） |
| 固定 seed 连翻 5 页（每页 24） | 120 条，去重后 120，**重复 0** |
| 同 seed 两次请求顺序 | 完全一致 |
| 20 次刷新首屏共 480 个位置 | 覆盖到 **478 个不同案件**（几乎零重复曝光） |
| 无 seed（`?page=1&limit=24&countryCode=CN`） | 按 created_at 倒序，与改动前一致 |
| 带 seed + `province=江苏省` | 仍按 created_at 倒序，2,280 条 |
| `seed=<script>` | 不报错，正常返回（降级为时间倒序） |
| 耗时 | 第 1 页 109ms，第 101 页 88ms |
