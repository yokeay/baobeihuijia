# 部署脚本化与部署后健康检查 — 技术方案

需求编号：REQ-202610-0450
分支：`req-202610-0450-deploy-script`

## 一、需求复述

来自开发路线图（REQ-202610-0267）卡 22：

- 【现状】部署为手工 build + `systemctl restart`，步骤易漏、构建期有服务不可用窗口。
- 【目标】`deploy.sh`：同步代码 → `npm ci`（按需）→ `npm run build` → restart → 健康检查（首页 200 + 关键接口抽查）→ 失败给出回滚提示。
- 【验收】一条命令完成部署；健康检查失败时明确报错。

## 二、现状

- 部署流程写在 README「部署」一节，共四步（`git pull` / `npm ci` / `npm run build` / `systemctl restart`），全靠操作者手工执行：没有部署前校验（分支、脏工作区、服务目录），没有部署后验证，`npm ci` 要么每次全量重装、要么凭记忆跳过。
- 服务器上已有独立的运维巡检：`/usr/local/bin/baobeihuijia-health.sh` + `baobeihuijia-health.timer`（每 2 分钟探测 `/api/stats`，连续 3 次失败自动重启服务）。它负责「事后自愈」，不覆盖「部署后立即验证」——本脚本的部署后健康检查与它互补，探测口径保持同类（本机回环 + 关键接口）。
- 服务由 `baobeihuijia.service` 托管：`WorkingDirectory=/root/baobeihuijia`，ExecStart 直接跑 `node node_modules/next/dist/bin/next start -p 3000`，内存上限 1500M、`Restart=always`。
- 线上验证不能走公网域名（Cloudflare 对命令行 UA 弹 403 挑战），必须走本机回环 `http://127.0.0.1:3000`。

## 三、设计

### 3.1 脚本位置与入口

`scripts/deploy.sh`（仓库运维脚本统一放 `scripts/`），`chmod +x`，`./scripts/deploy.sh` 一条命令跑完整个部署。支持参数：

| 参数 | 用途 |
| --- | --- |
| （无） | 完整部署 |
| `--no-pull` | 不拉代码，用当前工作区构建部署（回滚后重发用） |
| `--force-npm-ci` | 强制重装依赖（默认仅在依赖清单变化时执行） |
| `--health-only` | 只做健康检查，不部署 |
| `-h / --help` | 帮助 |

环境变量：`DEPLOY_BRANCH`（默认 `local-server`）、`SERVICE_NAME`（默认 `baobeihuijia.service`）、`HEALTH_BASE_URL`（默认 `http://127.0.0.1:3000`）、`HEALTH_TIMEOUT_SECONDS`（默认 60）。

### 3.2 部署前守卫（步骤易漏 → 不可能漏）

按顺序校验，任一不过即中止（全部在拉代码之前，不会改动线上）：

1. 脚本必须在 git 仓库内；以脚本自身位置定位仓库根目录。
2. 必须以 root 运行（`systemctl restart` 需要）。
3. `flock` 文件锁（`/var/lock/baobeihuijia-deploy.lock`）——防止两个部署并发跑。
4. 当前分支必须是 `local-server`（在 worktree / feature 分支上跑会被拒绝）。
5. 已跟踪文件必须干净（`git status --porcelain --untracked-files=no`）；未跟踪文件（如日志）不拦截。
6. 脚本所在仓库目录必须与服务 `WorkingDirectory` 一致（防止从其它 checkout 部署）。

### 3.3 五步流水线

```
1/5 同步代码   git fetch + git pull --ff-only origin local-server
2/5 依赖       npm ci（按需：node_modules/.package-lock.json 缺失、或 package.json / package-lock.json 比它新时才跑）
3/5 构建       npm run build（与手工流程同序：构建完再统一切换）
4/5 重启       systemctl restart baobeihuijia.service，15s 内确认 active
5/5 健康检查   轮询至多 HEALTH_TIMEOUT_SECONDS（默认 60s）：
               · 首页 /            → HTTP 200
               · /api/stats        → 200 且 JSON 含数值型 total
               · /api/cases?limit=1 → 200 且 JSON 含 items 数组
```

健康检查选这三项的理由：首页 = 整站可访问；`/api/stats` = 数据库查询链路（含缓存逻辑）；`/api/cases` = 核心业务列表接口（JSON 契约）。三项都走本机回环，不受 Cloudflare 影响。

### 3.4 失败处理：分阶段报错 + 回滚提示

- 任一步失败即以非 0 退出，错误信息指明**失败阶段与检查项**；
- 记录部署前版本 `PREV_SHA`，失败时输出统一提示块：`journalctl` 查日志命令 + 回滚命令（`git reset --hard PREV_SHA` + `./scripts/deploy.sh --no-pull --force-npm-ci`）；
- 构建失败时额外说明「服务未重启，线上仍是旧版本」；重启 / 健康检查失败时提示先看服务日志；
- 成败都写 `logger -t baobeihuijia-deploy`，可在 journal 里查部署史。

### 3.5 防凭据回显

远程 URL 内嵌了推送凭据，所有 git 命令输出统一经 `sed` 掩码（`https://***@…`）再打印，避免凭据进入终端日志或 journal。

## 四、改动清单

- `README.md` —— 「部署」一节改为推荐脚本入口，保留手工步骤作为回退。
- `docs/REQ-202610-0450-plan.md` —— 本文档。

## 五、验收标准

1. 一条命令（`./scripts/deploy.sh`）完成：同步代码 → npm ci（按需）→ 构建 → 重启 → 健康检查。
2. 健康检查失败时：非 0 退出、明确报出**哪个检查项**失败及原因，并输出回滚提示。
3. 部署前守卫覆盖：分支不符 / 脏工作区 / 服务目录不一致 / 并发部署，均拒绝且不动线上。
4. 部署成功后：服务 active、首页 200、关键接口正常；`logger` 有记录。
5. 不把任何凭据回显到日志。

## 七、已知但本次不改

- **构建窗口仍在**：`npm run build` 在服务运行时重建 `.next`，期间个别静态资源请求可能短暂失败（与手工流程完全同序，本次不改变风险面）。要消除需蓝绿/双目录切换，超出本卡范围。
- **flock 只锁脚本**：手工 `systemctl restart` 等操作不受锁保护；约定部署一律走脚本。
- **健康检查项固定为三项**，不做配置化；如需增减直接改脚本。
