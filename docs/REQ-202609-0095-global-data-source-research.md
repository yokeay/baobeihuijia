# 全球失踪人口数据源扩展调研

需求编号：REQ-202609-0095
分支：`req-202609-0095`
调研日期：2026-09-19
文档性质：**调研报告，不含代码改动**

## 一、需求与结论摘要

需求问的是「除了大陆、香港、美国，还有哪些地区能拿到公开数据」。本文逐个核验了需求点名的 12 个地区，并额外排查了跨国渠道。**所有 URL 均为 2026-09-19 实际访问验证**，记录真实 HTTP 状态码与 DNS 结果；下文标 🔴 的一律是**已验证不可行**，不是「没查到」。

### 1.1 主要结论

**① 能接，而且比预想的多 —— 但「官方公开个案库」在全球是稀缺品。**

需求点名的 12 个地区（英国/英格兰实为同一主体，合并计）中：

- **6 个有个案级源**：韩国、英国、法国、意大利、土耳其、泰国
- **其中 4 个无需任何授权即可立刻开工**：韩国、意大利、英国、法国，合计约 **2900 条**个案
- **4 个没有可用的公开个案源**：越南、印度、埃及、缅甸

**② 最值得先做的是韩国。** `안전Dream`（safe182.go.kr，韩国警察厅）是本次调研里**唯一「官方 + 个案级 + 含照片 + 服务条款明文允许非商业使用」的成熟 API**（约 1042 条，覆盖失踪儿童、离家出走者、残障人士、痴呆患者及身份不明者）。它的 ToS 要求「标注来源」+「非商业用途」，与本平台纯公益定位天然契合。唯一障碍是 `authKey` 申请需韩国手机本人认证，退路是解析其公开列表页（robots 未禁）。

**③ 几个必须如实说明的「看起来能用、其实不能用」：**

- **意大利 895 条、英国 552 条是「未确认身份遗体」，不是失踪者** —— 无姓名无照片，不能计入失踪人口数，只能单列类目或用于比对。
- **越南 7418 条是通缉犯** —— 字段再全，性质也不是失踪者。
- **印度三个中央寻人门户（TrackChild / Khoya Paya / ZIPNET）在 DNS 层就已失效** —— 不是被墙也不是改版，是域名本身没有权威解析。老文档里这三个地址不必再试。
- **俄罗斯内政部全站对境外 IP 封锁**（本机 TCP 443 全超时），不是配置问题，海外服务器同样够不着。

**④ 真正的扩量方向是跨国渠道，不是逐国找。** 逐国排查会发现大量国家根本没有公开个案库，而 **INTERPOL 黄色通报一次覆盖 190 国**、含照片与非拉丁姓名，正好命中「不想再拘泥于几个地区」的诉求 —— 但它被 Akamai 对数据中心 IP 整体拦截（实测 403），要么上浏览器渲染，要么向 INTERPOL 申请白名单，属高投入高天花板项，建议先做小规模可行性验证。

**⑤ 平台侧几乎不用动。** 接入任何新地区都是固定的四处小改动（新增 sync 模块、新增 admin 触发路由、加进 `SYNCED_COUNTRIES`、`countries.ts` 条目已存在）。`countries.ts` 里已列了 100 多个国家，但只有 CN/HK/US 有数据 —— 界面上其余国家筛出来全是空的，所以**新增任何一个国家都是净增量**。

## 二、平台现状与接入机制

### 2.1 现有数据源

| 地区 | 来源 | 实现 | 抓取方式 |
| --- | --- | --- | --- |
| 中国大陆 | 公开寻人数据聚合 | 主表 `cases` | 已有历史数据 |
| 香港 | 香港警务处失踪人士公告 | `src/lib/sync/hongkong.ts` | XML 列表 + 逐案详情 |
| 美国 | NamUs（DOJ） | `src/lib/sync/namus.ts` | REST JSON（州 → 检索 → 逐案详情） |

### 2.2 数据模型

每个国家/地区一张独立表（`cases`、`cases_us`、`cases_hk`…），由 `ensureCountryTable()` 按需建表，字段：

```
name / gender / birth_date / lost_date / lost_province / lost_city / lost_district
/ lost_address / height / feature / photo_urls / source / source_url / source_id
/ status / view_count / follow_count / missing_country
```

照片是**热链上游**，不本地转存。这决定了新数据源必须满足两个硬条件：**照片 URL 可以长期外链**、**每条记录有稳定的 `source_id` 与可回溯的 `source_url`**。

### 2.3 接入一个新地区需要改的地方

调研结论落到实施时，改动面是固定的四小处：

1. 新增 `src/lib/sync/<country>.ts`（照 `namus.ts` / `hongkong.ts` 的模式：拉列表 → 逐案详情 → 去重写入）
2. 新增 `src/app/api/admin/sync-<country>/route.ts`（后台手动触发 + dry-run）
3. 把国家码加进 `src/lib/db/country-helpers.ts` 的 `SYNCED_COUNTRIES`
4. `src/lib/countries.ts` 里该国的条目已经存在（`lang` / `regionType` 已配好），无需新增

也就是说：**只要确认了可用数据源，接入成本主要压在解析与字段映射上**，平台侧几乎不用动。

### 2.4 一个被低估的前提

`countries.ts` 里已经列了 100 多个国家和地区，但只有 CN / HK / US 有数据 —— 界面上其余国家筛选出来是空的。所以「扩大数据源范围」这件事，**新增任何一个国家的性价比都很高**：前端、语言包、地区选择器都是现成的。

## 三、逐地区调研

本节逐个核验需求点名的国家。所有 URL 均为 2026-09-19 实测（curl / WebFetch 直连，记录真实 HTTP 状态码）；**标 🔴 的表示已验证不可行，不是「没查到」**。评级口径：

- 🟢 **可直连**：公开可达、结构可解析、个案级、有照片，无需额外授权
- 🟡 **有条件**：可达但需授权 / 需浏览器渲染 / 个案量极少 / 只有非个案数据
- 🔴 **不可行**：无公开个案库、站点被墙、或只有统计汇总

### 3.1 韩国 🇰🇷 —— 官方 API 已存在，且明确允许非商业使用

**韩国的特殊性：这是本次调研里唯一「官方、个案级、含照片、且明文允许非商业使用」的成熟 API。**

- 端点：`POST https://www.safe182.go.kr/api/lcm/findChildList.do`，另有 `amberList.do`（失踪警报）与 `safeMap.do`
- 关键参数：`writngTrgetDscds[]` 可按对象类型筛选 —— `010` 儿童、`020` 离家出走、`040` 设施保护无亲属（含身份不明）、`060/061/062` 残疾、`070` 痴呆、`080` 其他；另有性别、姓名、日期区间、发生地、年龄区间过滤，`rowSize` 上限 100
- ToS 已读，三条硬约束：**仅限非商业用途**、**必须标注「[资料出处：警察厅]」**、**日限 1000 次调用**，且 1 人 1 key 禁共享、**6 个月未使用自动停用**
- 该 ToS 与本平台「纯公益、非营利」的定位天然契合，署名要求也正好落在「来源标注」上，属于少数**合规成本可接受**的源

**唯一的现实障碍是拿 key**：`authKey` 申请页走**韩国手机本人认证**，境外主体过不去。两条路 —— ① 找韩国合作方/志愿者代申请；② 退而解析 `lcmMssList.do` 列表页（HTML 分页 `pageIndex`，10 条/页共 71 页），列表页 robots 未禁。两条路都可行，差别只是「稳」与「名正言顺」。

**字段映射注意**：`occrAdres` 是**单个地址串**，需要自行切分 `lost_province` / `lost_city`；照片走 `blobImgView.do` 另抓。覆盖范围比字面「失踪儿童」宽 —— 含离家出走者、残障人士、痴呆患者、无亲属的身份不明者，实际是韩国警方的**综合失踪人口检索**。

> **勘误**：既有文档 `docs/international-missing-persons-api-research.md` 5.4 节把韩国源记为 `missingchild.mogef.go.kr`（女性家族部运营）。实测该域名**已下线**（DNS 解析失败，curl 返回 000），并非本次新发现的独立源。接入韩国时应以本文的 `safe182.go.kr`（警察厅）为准。这与 3.3 节英国源 `missingpersons.police.uk` 域名失效属于同一类问题：旧文档的外部链接未做存活校验，**接入前需重新确认域名**。

**越南的坑在于「字段全但性质错」**。7418 条记录、149 页、姓名/照片/户籍/罪名一应俱全，看起来是三国里最好的源，但它是**通缉犯数据库** —— 对象是犯罪嫌疑人，不是失踪者。塞进 `cases_xx` 会让「寻人」与「通缉」混为一谈，既不准确也有伦理问题。若平台愿意单开「通缉」类目可以接（约 3–4 人日，需模拟 ASP.NET `__doPostBack` 翻页），但**不应算作失踪人口数据源**。

**缅甸明确不建议**。不存在中立、可核验的公开个案源，军政府与 NGO 名单互斥且互相定性；任何个案公开都可能危及当事人及家属人身安全。这不是「抓不到」的问题，是**不该抓**。

**泰国是三国里最可能谈成的**。Mirror Foundation 有成熟的失踪人口个案库，字段（姓名/照片/失踪地）与 `cases_xx` 高度匹配，但走的是登录墙，必须**正式联系（1300 热线 / 项目邮箱）签数据共享协议**。技术侧另有前置工作：泰文姓名无词间空格，要做姓名切分与检索归一化，全案约 8–12 人日。

**三国共用的前置工作**：非拉丁文字的归一化 —— 泰文无词间空格、缅甸文连写、越南语变音符号，统一需 **NFC 归一化 + 去变音检索**。这是接入这三国的公共依赖，也是 `countries.ts` 里它们 `lang` 配置之外真正缺的一环。

**两个必须记下的事实**：

1. **旧域名已死**。流传最广的 UKMPU 地址 `missingpersons.police.uk` 现在 **DNS 授权服务器 REFUSED / 公共 DoH 解析 SERVFAIL**，数据库已整体迁到 `nationalcrimeagency.gov.uk/missingpersons`。本项目 `docs/international-missing-persons-api-research.md:153` 引用的正是这个旧域名，本报告一并更新（该文档 5.1 节其余结论仍然成立）。

### 4.1 INTERPOL Yellow Notices —— 价值最高，但要先解决反爬

唯一真正全球、跨 190 国、个案级且带照片与非拉丁姓名的盘子，也是唯一能稳定带来中文姓名的国际渠道。

- 公开检索页可达：<https://www.interpol.int/en/How-we-work/Notices/Yellow-Notices/View-Yellow-Notices>（HTTP 200）
- 页面前端调用的端点是 **v2**：`https://ws-public.interpol.int/notices/v2/yellow`（历史文档里流传的是 v1，路径已更新）
- **实测 403**：v1 / v2 / 该主机 `robots.txt` 全部 403（Akamai Access Denied）。补 `Referer`/`Origin`/`X-Requested-With`/`Accept`、带会话 cookie、HTTP/2、换出口 IP（WebFetch）均 403 —— 是对**数据中心 IP 的整体拦截**，不是参数问题。
- 可用的旁支 JSON（www 域，非通报本体）：`https://www.interpol.int/en/notices/data/grouped_countries`、`.../grouped_nationalities` → 200，仅为筛选下拉的国家/国籍清单。
- `https://www.interpol.int/robots.txt` → 200，`Disallow: /en/Search-Page`（不欢迎抓检索页）。
- 字段：姓名、性别、出生日期、国籍、失踪时间地点、照片 —— 与 `cases_xx` 表基本可一一映射。

**结论**：浏览器可正常访问，自动化接入被 WAF 拦。要走这条路需**浏览器渲染**（Playwright 等）或向 INTERPOL 申请数据白名单。建议先做小规模可行性验证（能否用无头浏览器稳定取到列表 + 详情，QPS 上限多少）再决定是否投入，工作量大且随时可能失效。

### 4.2 民间档案站（低成本、立刻上量）

- Charley Project <https://charleyproject.org/>、Doe Network <https://www.doenetwork.org/>：HTTP 200，Robots 允许，有 sitemap，个案级且带照片，纯 HTML 解析即可，接入成本约 1–2 人日。
- 局限：**以美洲为主**，非全球覆盖；属民间二手档案，需在来源标注里写清「数据来自民间档案，非官方源」，不能与官方源同级展示。

### 4.3 明确排除

ICRC、ICMEC GMCN、Missing Children Europe / 116000、澳洲 NMPCC、各政府开放数据门户：均**没有公开的个案级数据库**，只是宣导页、热线网络、统计汇总或 PDF 海报。开放数据门户即便有 API，命中的也是「汇总统计」类数据集，对个案聚合无价值。

## 五、接入优先级建议

按「字段匹配 × 合规成本 × 可落地性」排序。接入动作本身是固定的四小处改动（见 2.3），差异全在数据源。

### 扩源之前建议先补的三件基础设施

这三件不是新源的附加项，而是**新源的前置条件** —— 源越多，缺了它们的代价越大：

1. **撤回/下架机制**（见 6.2）。当前 `removed` 恒为 0，`hongkong.ts` 连字段都没有。接新源前应补上「上游已消失 → 本地软下架」，尤其因为失踪数据的「已找到」状态必须及时体现。
2. **照片可用性巡检**（见 6.4）。全部热链上游，源一多，上游改 URL 或加防盗链就会成片裂图。
3. **非拉丁文字归一化**（NFC 归一化 + 去变音检索）。韩、泰、越、缅四国共用，是它们「能查到」的前提。

## 六、合规与风险基线

调研过程中反复撞到同一组问题，它们决定「能不能接」而不只是「好不好接」。按严重度排列：

### 6.1 数据性质：这是敏感个人信息，不是公开新闻

平台聚合的是**真实个人的姓名 + 照片 + 失踪时间地点 + 体貌特征**。在中国《个人信息保护法》下属敏感个人信息（涉及人身安全），在 GDPR 下叠加「儿童数据」时属于最高风险档。源站主动公开个案，等于源方已经完成了公开决定；我们**转引已公开信息**与**首次公开**责任的量级完全不同 —— 前者是聚合，后者是发布。这条线必须守住：**只接源方已经主动、无偿、面向公众公开的个案**，不碰需要申请、登录、或受保护令约束的记录。

### 6.2 撤回机制：现状是只增不减（已存在的技术债）

`namus.ts` 的统计结构里有 `removed` 字段，但三处赋值**全部恒为 0**（`namus.ts:232/285/418`）；`hongkong.ts` 连这个字段都没有。两个同步逻辑都只做插入与跳过，从不回查上游是否已撤案或已找到人。失踪人口数据和其他数据不同：**「已找到」是这个数据集里最需要及时体现的状态**，一条已团圆记录继续挂着是对当事人和家属的二次伤害。

接新源时建议同步补上：同步完成后拉取上游当前全量 `source_id` 集合，本地存在而上游已消失的标记下架（软删除，不物理删）。这是一处独立的小改动，但**应该是所有新源的前置条件**。

### 6.3 来源标注与分级展示

- 每条记录必须带 `source` / `source_url`，可回溯到原始页面（现有表结构已支持）。
- **官方源与民间档案不能同级展示**。Charley Project、Doe Network、ARPD、Penelope 都是民间/协会档案，需在界面上明确标注「数据来自民间档案，非官方发布」，否则用户会误把二手信息当权威信息，反过来损害平台公信力。
- 意大利 RNCNI 是**无名尸体**数据，无姓名无照片，必须单列类目（如「未确认身份遗体」）或仅用于比对，**不得计入失踪人口数**。

### 6.4 照片热链的双面性

不本地转存、只热链上游，客观上降低了复制与再分发风险，也让「撤下上游即撤下本站」在理论上成立。但反过来：上游改 URL、加防盗链、或下架照片，本站会立刻出现大量裂图 —— README 待办里「照片全部热链上游，未做本地缓存与失效检测」说的就是这件事。接入源越多，这个面越大（NamUs 已有 2 万余张照片依赖外链）。**建议在扩源之前先补一个照片可用性巡检**，否则新增的源会同时放大裂图问题。

### 6.5 robots.txt 与站点条款逐一确认

实测差异极大，不能一概而论：INTERPOL 的 `robots.txt` 明确 `Disallow: /en/Search-Page`（不欢迎抓检索页）；ARPD 的 robots 允许内容抓取（只禁 Drupal 默认的管理路径）；意大利 `commissari.gov.it` 是 `Allow: /`。**每接一个源，先读该站 robots.txt 与使用条款，并在 `src/lib/sync/<country>.ts` 顶部注释里写明许可依据**，让合规状态能随代码一起被审计。

### 6.6 未成年人数据的额外约束

116000（法国）、NCMEC（美国）等儿童专项源，照片发布通常须警方授权 + 家属同意，自动抓取基本不可行。建议**默认排除**需要单独授权的未成年人记录，只接官方已主动公开的部分，且不做任何面部加工或增强。

**三处与本文初版预判不同的地方**，值得记下：

1. **照片不是热链，必须中转**。`blobImgView.do` 有两台后端在应答而 blob 不同步，取不到图时返回的是一个 **2860 字节的警方徽章图**（sha256 `a2469b43…af5bb`）而不是 404 —— 热链会让卡片显示同一个徽章冒充人脸。因此实现了带会话保持 + 占位图识别 + 会话轮换的中转路由 `/api/image/safe182/[id]`，命中占位图时判 404 并换会话重试（最多 5 次）。
2. **`hasPhoto` 严重高估，可用的照片很少**。列表页只要有 `<img src="blobImgView...">` 就记为有照片，所以 789 是**照片字段数**，不是可用照片数。实测可用率很低：
   - 跨 id 段随机抽 62 条（每段 6 条），只有 3 条取到真实图片，且这 3 条**全部**是 id ≥ 6179149 的最新记录；
   - 拿最新的 40 条「有照片字段」的记录过中转路由，两次分别 **20/40** 与 **10/40**；
   - 同一个 id 反复探测，结果会在「真图 / 占位图」之间来回跳：6179525 先后测到 6/12 → 16/16 → 8/8 → 0/4；
   - 但**较老的记录是确定性失效**：4528830 与 3980630 分别反复探测 24 次和 14 次，**全部**是占位图。

   即可用照片基本集中在最近几十条记录，且这段窗口内也时好时坏。**已复核确认这不是中转路由的问题**：对同一批 39 个 id，同一时间直连上游与走中转路由的字节结果 **37 个完全一致**（剩下 2 个是上游在几分钟内自己翻转的）。上游到底是「两台后端里只有一台还有 blob」还是「老记录被清理、新记录尚未同步到另一台」，本次未能定论，此处只记录可复现的现象。

3. **`발생장소` 不总是以市道开头**。约 124 条是「개포로303 개포현대1차아파트 103동」这类不带市道前缀的街道地址，落在「无法驱动地区筛选」的分支里 —— 原文保留在 `lost_address`，但 `lost_province` 为空。

### 7.3 新发现：西班牙 CNDES（不在原 12 国清单内）

复核过程中撞到一个原调研没覆盖的源，质量足以进 P0：

| 项 | 值 |
| --- | --- |
| 站点 | `https://cndes-web.ses.mir.es/publico/Desaparecidos/` |
| 运营方 | 西班牙内政部 失踪人口与失踪者国家中心（CNDES） |
| 列表接口 | `POST /publico/Desaparecidos/dao/ServletDesaparecidos`，`operacion=buscar&start=0&max=100&locale=es` |
| 返回 | **JSON**，`{totalRegistros, desaparecidos[]}` |
| 量级 | **525**（`totalRegistros`） |
| 字段 | `id` / `nombreCompleto` / `genero` / `tipoDesaparecido`（MENOR/ADULTO/MAYOR）/ `fechaDesaparicion` / `resumenWeb` / `necesidades` / `cuerpo`（办案警队）/ `telefono` / `tipoAlerta` / `localizado` / `foto`（**base64 JPEG 内联**） |
| robots | 无限制 |

**三个必须知道的坑**：

1. **`start` 必须显式给 0**。留空（`start=`）服务端会返回 `{"aviso":"Error interno, intentelo más tarde."}` 而不是数据 —— 本文初版记的正是留空写法，是错的。
2. **单次查询硬上限 100 条**。`start=0&max=100` 恰好返回 100 条；`start=100&max=100` 返回 `{"aviso":"No se han encontrado resultados..."}`。所以不能靠 `start` 翻完全量，必须**按年份切片**：`anioDesaparecido=2026` → 84 条、`=2015` → 8 条、`=2010` → 6 条，每个年份都远低于 100，枚举因此可行。年份过滤参数已实测有效。
3. **响应很大**。100 条 = **27.6 MB**（照片是内联 base64，单张约 300 KB）。按年份切片枚举反而顺带把这个压力摊开了。
2. **姓名是脱敏的**。`nombreCompleto` 形如 `María Del Rosario G. G.`，姓氏被缩成首字母。这是源站的公开口径，不是解析问题 —— 接入后卡片的姓名会比中/韩/美源明显更弱，需要在展示层接受这一点。

评级 **🟢**：官方、公开、结构化 JSON、含照片、无需授权，解析成本仅高于 RNCNI。唯一需要额外处理的是年份切片循环与 base64 照片转存/中转。
