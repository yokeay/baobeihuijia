# 访问数据统计（访问卡片 + 访问趋势折线图） — 技术方案

需求编号：REQ-202609-0135
分支：`req-202609-0135`

## 一、需求复述

后台仪表盘加一块流量统计：

1. 统计卡片：**累计访问次数**、**累计真实访问 IP 数（不重复）**。
2. 整站**被浏览的总次数**，**刷新一次算一次访问**。
3. 再加**一条折线图**看访问趋势 —— 仪表盘原来已经有 4 个统计图，这是在它们之外**新增的第 5 个**。

## 二、现状问题

1. 仪表盘只有案件/线索/关注三类业务数据，**完全没有流量视角**。案件总数涨了到底是推广有效还是自然增长，看不出来。
2. 现有的 `user_activities` 只记登录用户的行为（关注等），**匿名访客完全不可见** —— 而本平台绝大多数访问都是未登录的匿名流量。
3. 案件自带的 `views` 字段是「单条案件的浏览量」，不是全站访问量，且新导入数据带 3000–5000 随机起始值，**不能拿来做平台级统计**。
4. `/api/admin/trends` 此前是**匿名可取**的（只有后台仪表盘在读它，没做鉴权）。现在要往里塞流量序列，就不能继续裸奔。

## 三、设计方向

- **埋点位置选根布局**。Next.js App Router 的根布局**只在整份文档加载时挂载一次**，客户端路由跳转不会重挂。把上报组件挂在根布局，就让「刷新一次 = 一次访问」成为**结构性保证**，不需要额外去重逻辑。（若埋在页面组件里，站内跳转也会计数，与需求不符。）
- **不上 cookie、不做会话去重**。需求要的是「访问次数」= 页面加载次数，不是 UV 会话数，所以一次加载一条流水，用最简单的模型。
- **IP 只以哈希落库**。隐私政策白纸黑字写着「我们**不存储**您的 IP」，所以原始 IP 绝不入库：只存 `HMAC-SHA256(JWT_SECRET, ip)`。同一 IP 得到同一哈希 → 能 `COUNT DISTINCT` 出独立访客数，但没有密钥就**不可逆推**。
- **不引新密钥**。HMAC 的 key 直接用已有的 `JWT_SECRET`，避免新增一个需要进部署流程的 secret，也就不需要写「key 缺失时的兜底分支」。
- **机器人天然被排除**。上报走 JS beacon，不执行 JS 的爬虫根本不会发这条请求 —— 「真实访问 IP」这条不用额外写 UA 黑名单。
- **管理员自己不算访客**。前后端各判一次 `path.startsWith("/admin")`：管理员天天开后台，否则统计会被自己刷高。
- **统计失败绝不影响页面**。接口整体 try/catch，页面照旧返回，流水丢了就丢了。

### 4.3 数据表

```sql
CREATE TABLE IF NOT EXISTS site_visits (
  id TEXT PRIMARY KEY,
  ip_hash TEXT NOT NULL,
  path TEXT,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()
);
```

`created_at` 与 `ip_hash` 各建一个索引：前者供趋势线按天分桶与「今日」筛选，后者供 `COUNT DISTINCT` 出独立访客。

**建表方式沿用仓库既有约定**：仓库的 `drizzle/meta/_journal.json` 是 `"entries": []`，没有任何自动迁移机制，`0001_user_activities.sql`、`0002_comments_moderation.sql` 也都是手写 SQL 文件、部署时手工 psql 执行。所以本次同样只交付 `.sql`，**不加进 `initDb()`**（否则会和既有约定打架）。

### 4.4 关键实现细节

- **计数器怎么算**：一条 SQL 出四个数 —— `COUNT(*)`、`COUNT(DISTINCT ip_hash)`、以及各自 `FILTER (WHERE created_at >= CURRENT_DATE)` 的今日版本。
- **时区**：「今日」用 `CURRENT_DATE`（数据库会话时区，本机是 Asia/Shanghai），趋势线用 `DATE(created_at)` —— 两者走同一套时区，**不会出现卡片和折线图对不上**的情况。
- **`sendBeacon` 优先**：页面正在卸载时 `fetch` 会被中断，`sendBeacon` 是浏览器保证送出的；不支持时才退回 `fetch(..., { keepalive: true })`。
- **严格模式双跑**：React 严格模式下 effect 会执行两次，组件外用模块级 `reported` 标记，保证一次加载只上报一条。
- **访问趋势单独取数**：现有三个图表共用 `caseRange`（`clueRange` / `followRange` 是历史遗留的空转选择器）。第 4 张图配了自己的 `visitRange` 状态与 `fetchVisitTrends()`，所以它的区间选择器**是真的能用**的。
- **`fill()` 补齐空缺日期**：趋势接口沿用既有的日期补齐函数，没有访问的日子补 0，折线不会断。
- **保留既有行为**：`stats` 接口原有字段逐字节不变，只**追加** `visits`；`trends` 只**追加** `visits` 序列。

## 六、风险

- **表要先建好再切流量**。访问接口直写 `site_visits`，表不存在会走 catch 静默吞掉 —— 不会 500，但**统计静默不涨**，不容易被察觉。所以部署顺序必须是「apply SQL → build → restart」，且上线后**必须**验一次 `count(*)` 确实在涨。
- **没有数据迁移**。上线即从零开始计，历史的访问量补不回来（本来也没有历史数据源）。
- **IP 哈希的粒度**：同一出口 IP 下的多个真实用户会被算作一个独立访客（高校/公司/移动网络共出口常见），所以「独立 IP」是**偏低的估计**，卡片 hint 里写明了是按访客指纹去重。
- **IPv6 与代理头**：取 `x-forwarded-for` 第一段，站点前置 Cloudflare，正常情况下该头可信；若日后绕过 CF 直连源站，该头可被伪造，独立 IP 会被刷高。
- **流水只增不删**：目前没有清理策略，长期会持续增长。日访问量级很小，暂时不处理；但若日后流量上来，需要补一个按保留期归档的定时任务。
