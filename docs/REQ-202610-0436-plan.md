# 数据库每日备份与异地副本 — 技术方案

需求编号：REQ-202610-0436
分支：`req-202610-0436-db-backup`；部署分支：`local-server`；站点：wohaoxiangni.com

## 一、需求复述

- **频率与保留**：初稿为「每周一次、最多保存两周、第三周删上上周」；修订版 5(a) 改为「每天进行一次增量备份。这样就不需要限制说删哪一周的数据了」。
- **存储与分片**：数据超过 GitHub 单文件上传限制就分片。
- **格式与增量**：(a) SQL 文件，直接存建表语句 + 插入语句；(b) 只备份增量数据，没有更新的不备份。
- **基础备份**：把数据库表做一次性基础备份，记好文件夹名字。
- **每日增量与远程提交**：(a) 每天一次增量；(b) 通过脚本触发把每天更新的数据提交到远程；(c) 失败时保留日志并写入系统数据库的日志信息表，由脚本维护。
- **验收**：备份文件按期生成、可恢复；完成一次恢复演练并记录耗时。
- **安全红线**：备份含敏感个人信息——不进主仓库、不公开（异地副本仅进私有仓库）。

## 二、现状（2026-10-13）

- 无任何备份任务；仅 2026-07-08 一次手工转储 `database_dump.sql`（35 MB，且随主仓库跟踪——其去留属路线图卡 25，不在本需求范围）。
- 生产库：Docker 容器 `infra-postgres`（PostgreSQL 16.14，TZ=Asia/Shanghai），库 `baobeihuijia`，用户 `baobei`；28 张表（27 张原有 + 新增 `system_logs`）。
- 主仓库部署分支 `local-server`，无 CI，部署走 `scripts/deploy.sh`；服务器为 UTC 时区，cron 已有香港同步（03:07）、镜像同步（03:37/03:47）、paper-reader 备份（04:23/23:30）等任务。

## 三、设计

### 3.1 总体流程

每日 cron → `scripts/db-backup.sh` →（首次或 `--rebuild-base`）基础备份 /（之后）增量 → 自检 → 提交并推送到私有仓库 `yokeay/baobeihuijia-db-backup` → 更新本地状态。

- 单实例锁（flock），失败退出码非 0；cron 把 stdout/stderr 追加到 `/var/log/baobeihuijia-db-backup.log`（超 1 MB 自截断、保留最后 2000 行）。
- 推送凭据从主仓库 `remote.origin.url` 内嵌 PAT 提取（不落盘、不回显；日志统一掩码）。

### 3.2 备份格式与分片

- plain SQL、`--column-inserts`（每行一条 INSERT）：`CREATE TABLE` + `INSERT`，满足需求 3(a)「最简单最直接」。
- 单文件超过 95 MiB（GitHub 单文件硬限 100 MiB，留余量）→ `split -C` 按行边界切为 `*.part-01/02/…`；**重组 sha256 必须与原文件一致、单片必须 < 100 MiB**，否则判失败并清理。
- `base/base-YYYYMMDD/` 内 `MANIFEST.json` 记录：文件夹名、文件名、字节数、sha256、表数/行数、分片数与重组命令——「记好文件夹名字」的落点。

### 3.3 增量口径

- 每表按「变更时间」过滤，窗口起点 = 上次成功起点 − 10 分钟（重叠防漏；边界重复无害，语句幂等）。
- 分组：
  - 案件表（14 张，cases/cases_at/…/cases_us）：`GREATEST(updated_at, reviewed_at)`（文本空串用 nullif 归一）；
  - 流量表（case_views/site_visits/audit_logs/user_activities）：`created_at`；
  - 小表（users/admins/settings/follows/comments/questions/feedback/clues）：每次全量携带（体量小、无可靠变更时间戳，保证一致性）；
  - sync_runs：`GREATEST(started_at, coalesce(finished_at, started_at))`。
- 时区：psql 会话钉死 `TimeZone=Asia/Shanghai`（与线上 timestamp 语义一致）；`timestamptz` 列按 UTC 边界比较，边界值来自状态文件的 `last_success_start_utc`。
- 语句幂等：`INSERT … ON CONFLICT (主键) DO UPDATE SET 非主键列 = EXCLUDED…`；表顺序满足外键依赖；文件含 `SET standard_conforming_strings = on; BEGIN; … COMMIT;` 与逐表节注释；生成后自检语句总数。
- **覆盖守卫**：线上出现「未登记进策略」的新表 → 拒绝生成、失败告警（防止未来加表后静默漏备）。

### 3.4 失败处理与 system_logs（需求 5(c)）

- 失败时：① 日志留在 LOG_FILE（cron 追加）；② 写失败标记 `/root/baobeihuijia-backups/.last-backup-failed`（含原因与时间）；③ 尽力写系统库 `system_logs` 表（数据库不可达时自动跳过——此时标记与日志仍保留，不掩盖主错误）。
- 迁移 `drizzle/0006_system_logs.sql`：`system_logs(id, level, source, message, detail, created_at timestamptz)` + `created_at DESC` 索引；`CREATE TABLE IF NOT EXISTS` 可重复执行；`src/lib/db/schema.ts` 同步导出 `systemLogs`（应用侧只读，后台如需展示再挂路由）。
- 注意（测试抓出的坑）：psql 的 `-c` 不做变量插值，写库必须走 stdin（`-f -`）才能用 `:'var'` 安全传值——已修复并由冒烟测试钉住。

### 3.5 保留策略

- 两处需求口径并存（见「需求复述」）。按修订版 5(a) 落地：**默认保留全部**（`RETENTION_DAYS=0`）；如需滑动窗口可设天数（>0 时删除 N 天前增量文件）。
- 风险提示：增量是链式 delta，删除旧增量会破坏「基础备份 + 增量」恢复链；启用删除时必须配套定期 `--rebuild-base`。已提交平台决策项（Jev 校准：保留全部 1.00）。

### 3.6 运行与状态

| 项 | 位置 |
|---|---|
| 状态文件 | `/var/lib/baobeihuijia-db-offsite/state.json`（上次成功起点、基础备份文件夹名、上次增量） |
| 备份仓库工作副本 | `/var/lib/baobeihuijia-db-offsite/repo`（private 仓库克隆） |
| 失败标记 | `/root/baobeihuijia-backups/.last-backup-failed` |
| 日志 | `/var/log/baobeihuijia-db-backup.log`（cron 追加） |
| 锁 | `/var/lock/baobeihuijia-db-backup.lock`（flock 单实例） |
| 备份仓库 | `yokeay/baobeihuijia-db-backup`（private，每次推送前断言） |

### 3.7 恢复流程

1. `git clone` 备份仓库（需有权限的账号）；
2. 建一个空 PostgreSQL 16 库（导出用 `--no-owner --no-privileges`，不要求同名角色）；
3. 恢复最新 `base-` 文件夹（分片先按 `MANIFEST.json` 的 `reassemble_cmd` 合并）：
   `psql -v ON_ERROR_STOP=1 -d <目标库> -f base/base-XXXXXXXX/baobeihuijia_base_*.sql`
4. 按文件名顺序依次应用 `increments/`（幂等，可重复执行）。

## 六、已知限制

- **计数器静默更新不进增量**：`cases.view_count / follow_count` 由浏览/关注操作静默 UPDATE（不触发 `updated_at`），备份中计数可能滞后，直到该行因其他原因被捕获或重做基础备份。已提交平台决策项（Jev 校准：接受现状 0.89——计数为辅助展示数据）。
- 增量链式：恢复必须从最近一次 `base` 起按序应用全部增量；不建议手工挑删增量。
- 恢复演练为同机演练（同一 PostgreSQL 实例新建 scratch 库）；异地整机恢复未演练。
