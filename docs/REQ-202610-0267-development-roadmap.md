## 二、总体思路

一句话：**先让数据可信，再让数据变多，然后让需要的人找到它、能反馈，最后做深化。**

1. **可信优先**：失踪数据的「已找到 / 已撤案」必须及时下架（0095 §6.2 点名现状「只增不减」）；照片不能成片裂图；来源要能追溯、能分级。没有这三样，数据越多，伤害越大。
2. **扩源其次**：英、法、西约 1,500 条是「已逐一复核、确定性可落地」的收益（0095 §7.5），在三件前置补齐后即可开工。
3. **触达第三**：访问 4.7k、用户 3 —— 价值的放大器是搜索引擎与分享（现状：sitemap 仅覆盖大陆且截断 1 万条、无 hreflang；分享卡依赖上游热链照片，失效即无图）。
4. **闭环第四**：提交 / 线索目前「交完就没了」——补回执查询与案件纠错入口，让反馈有去处、有回音。
5. **一切以「家属与志愿者用得上」为准绳**，不引入与定位不符的社区化、娱乐化功能。

### 4.0 阶段零 · 决策（3 张）

**01 · 规划落地顺序与节奏〔决策卡〕**（阶段零 · 依据：0095 §5）
【现状】本规划 25 张卡中，三件基建（04/05/13）是扩源（10/11/12）的前置条件（0095 §5 明确「源越多，缺了它们的代价越大」），但先做哪边会直接影响「多久能看到新数据」。【目标】维护者拍板：**A 先基建后扩源（推荐，Jev 校准 1.00——敏感数据「只增不减」的风险优先于上新量）/ B 先扩源后基建 / C 并行推进**；决定后续 22 张卡的启动顺序与验收节奏。

**02 · 新源照片本地化策略〔决策卡〕**（阶段零 · 依据：0095 §6.4）
【现状】照片全部热链上游（NamUs 2 万余张）：好处是「上游撤下即本站撤下」，代价是上游改 URL / 加防盗链即成片裂图；韩国已因占位图问题必须中转，西班牙 CNDES 照片为 base64 内联、**无法热链**。【目标】维护者拍板：**A 维持热链为主 + 巡检兜底，仅对无法热链的源（韩 / 西）本地中转（推荐，Jev 校准 0.98）/ B 全面本地转存 / C 维持纯热链现状**；决定 05/10/11/12 的照片处理方式与存储投入。

**03 · 更正与下架请求受理口径〔决策卡〕**（阶段零 · 依据：0095 §6.1 / §6.2）
【现状】失踪数据属敏感个人信息，「已找到」必须及时体现；当前无任何下架机制（`removed` 恒为 0），也无申请受理口径。【目标】维护者拍板：**A 双轨：上游消失自动软下架 + 家属 / 本人 / 警方申请经核验后人工下架（推荐，Jev 校准 1.00）/ B 仅做自动软下架、不受理申请 / C 开放自助下架（仅邮箱验证、无人工核验）**；决定 04/06 的处理流设计。

### 4.1 阶段一 · 地基（6 张）

**04 · 上游撤案软下架机制（同步回查 + 软删除）**（阶段一 · 预估：中 · P1 · tech_debt · 依据：0095 §6.2）
【现状】三个同步（`namus` / `hongkong` / `korea`）只做插入与跳过、从不回查上游；`namus.ts` 的 `removed` 统计恒为 0（232/285/418），`hongkong.ts` / `korea.ts` 连该字段都没有；表也无软下架列（`cases` 仅 approved / pending / rejected）。【目标】同步完成后拉取上游当前全量 `source_id` 集合，本地有、上游已消失的记录 → 软下架（新增 `removed_at` 类标记，不物理删）；已找到记录从默认列表移除、详情页明示状态；后台可查看与手动下架。验收：抽一个上游已撤案样本，同步后本地状态变化且不再出现在默认列表。

**05 · 照片可用性巡检与裂图兜底**（阶段一 · 预估：中 · P1 · tech_debt · 依据：0095 §6.4）
【现状】照片全部热链上游，无缓存与失效检测（README 待办原文）；上游改 URL / 防盗链即成片裂图；韩国中转路由已有占位图识别能力可复用。【目标】定期巡检（抽样或全量 HEAD / 占位图识别），失效照片打标记并在界面兜底（占位图 / 隐藏）；输出巡检报告；与 15 / 24 联动。验收：随机抽样一批失效 URL，巡检能识别并兜底展示。

**06 · 案例纠错入口与后台处理流**（阶段一 · 预估：中 · P1 · feature · 依据：0095 §6.2）
【现状】仅有整站「反馈与建议」（0144），案件维度没有「信息有误 / 已找到」上报入口，也没有处理流。【目标】案件页新增纠错入口（类型：信息错误 / 已找到 / 请求下架），进入后台独立队列；处理动作与 04 的软下架联动；匿名可提交（联系方式可选）。验收：从案件页提交一条纠错 → 后台队列可见 → 可执行下架联动。

**07 · 来源分级标注（官方源 / 民间档案）**（阶段一 · 预估：小 · P2 · enhancement · 依据：0095 §6.3）
【现状】详情页已展示来源名称与「查看来源」链接，但无官方 / 民间分级概念（大陆聚合与港 / 美 / 韩官方源混同展示）。【目标】来源规范化（每源标准名 + 级别）；界面区分「官方发布」与「民间档案」；为 18 的民间源接入做准备。验收：抽样各源详情页，级别标注正确、可回溯。

**08 · 数据库每日备份与异地副本**（阶段一 · 预估：小 · P1 · enhancement）
【现状】无任何备份任务；仅 2026-07-08 一次手工转储（且进了 git，见 25）。【目标】每日 `pg_dump`（压缩 + 轮转保留）到独立目录 + 异地副本；**备份含敏感个人信息，绝不进 git、不公开**；完成一次恢复演练并记录耗时。验收：备份文件按期生成、可恢复。

**09 · 同步任务与站点巡检告警**（阶段一 · 预估：中 · P1 · enhancement）
【现状】香港同步每日 03:07、美 / 韩手动触发；无失败告警、无站点巡检；「30 天 0 新增」无人知晓是正常还是坏了。【目标】巡检脚本（同步任务心跳与结果、站点首页 200、数据量突变）→ 异常时告警到维护者（渠道实现时选定）；输出周报或月报摘要。验收：人为制造一次失败，告警可达。

### 4.3 阶段二 · 触达（3 张）

**13 · 检索增强：文字归一化与容错匹配**（阶段二 · 预估：中 · P1 · enhancement · 依据：0095 §5）
【现状】列表筛选已较全（国家 / 省市区 / 性别 / 关键词 / 随机种子）；快捷搜索仅支持 q + 省市；非拉丁文字（韩、法、西等）无 NFC 归一化与去变音，检索命中率受损。【目标】① 文字归一化（NFC + 去变音）② 常见错字 / 别名容错（可选）③ 快捷搜索补充时间范围等字段。验收：韩文组合字符、法文变音符号可等价命中。

**14 · 案例页 SEO 补全：sitemap 覆盖与 hreflang**（阶段二 · 预估：小 · P2 · enhancement）
【现状】案件页已有 canonical、JSON-LD（Person）与 OG 元数据；但 sitemap 仅覆盖大陆 `cases` 且**截断 10,000 条**，美国 26,594 条完全不在 sitemap；无 hreflang。【目标】① sitemap 分片（`generateSitemaps`）覆盖全部已同步区表 ② 补 hreflang（10 语言）③ 核查 robots 与搜索引擎索引状态。验收：sitemap 索引可枚举全部区表条目，hreflang 输出正确。

**15 · 分享卡兜底：无有效照片时生成动态分享图**（阶段二 · 预估：小 · P2 · enhancement）
【现状】OG 图直接使用案件照片（热链）：无照片或热链失效时分享卡无图（韩国大量记录无可用照片）。【目标】为无有效照片案件生成品牌化动态分享图（姓名 / 地区 / 站点标识；不改变肖像使用口径）；与 05 的失效检测联动。验收：无照片案件在微信 / X 等平台分享时展示兜底图。

### 4.4 阶段二 · 闭环与效率（2 张）

**16 · 提交与线索进度查询（回执码）**（阶段二 · 预估：中 · P2 · feature）
