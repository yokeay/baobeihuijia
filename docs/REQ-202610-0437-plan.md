# 同步任务与站点巡检告警 — 技术方案

需求编号：REQ-202610-0437
分支：`req-202610-0437-inspect-alert`

## 一、需求复述

- 【现状】香港同步每日 03:07 由 cron 触发，美国/韩国/西班牙为手动触发；同步失败没有任何告警；站点没有巡检；「30 天 0 新增」无法区分是正常（上游确实没有新数据）还是故障（同步早就挂了）。
- 【目标】巡检脚本：同步任务心跳与结果、站点首页 200、数据量异常 → 异常时告警到维护者（渠道实现时选定）；输出周报/月报摘要。
- 【验收】人为制造一次失败，告警必须可达。

## 二、现状

- **同步无记录**：4 个来源的同步只有 stdout/`crawler.log`（香港 cron 把响应体追加到 `/opt/baobeihuijia/crawler.log`），数据库里没有「最近一次同步何时跑、结果如何」。`audit_logs` 只记后台登录与审核动作，不含同步。
- **站点无巡检**：服务器上有 `/usr/local/bin/baobeihuijia-health.sh`（每 2 分钟探 `/api/stats`，连续 3 次失败自动重启服务）——它是**事后自愈**，不告警、不覆盖数据量与同步检查，与本次工作互补。
- **无告警渠道**：此前任何异常都要靠人工翻日志才能发现。
- 部署：Next.js + systemd（`baobeihuijia.service`），部署走 `scripts/deploy.sh`（REQ-202610-0450）。

## 三、设计

### 3.1 同步运行记录：`sync_runs` 表

每次真实同步（非 dryRun）写一行，解决「心跳与结果」无结构化数据的问题。

- 迁移 `drizzle/0005_sync_runs.sql`：`id / source / status / started_at / finished_at / total_in_api / added / skipped / errors / duration_ms / last_error / detail(JSONB)`，索引 `(source, started_at DESC)`；`CREATE TABLE IF NOT EXISTS` 可重复执行。
- `src/lib/sync/runs.ts`：`beginSyncRun()` 插入 running 行；`completeSyncRun()` 完成时按 `errors > 0 → error / 否则 ok` 落结果，`detail` 存来源特有字段（NamUs 的 removed、CNDES 的 photosSaved）；`abortSyncRun()` 中途抛错记 failed。**记录失败绝不影响同步本身**（所有函数只记日志、不抛错）。
- 5 个同步入口（4 个国家级路由 `sync-hongkong / sync-namus / sync-korea / sync-cndes` + 遗留大陆爬虫 `/api/sync`）在真实运行时包一层 begin → complete/abort；dryRun 不记录。大陆爬虫的 `tokenMissing` 按错误记（爬虫并未真正开始跑）。

### 3.2 巡检脚本：`scripts/inspect.ts`

单文件、自包含（`pg` + `dotenv` + 全局 fetch，不依赖 `@/` 别名），可由 systemd 或手工运行。三类检查：

| # | 检查 | 口径 | 告警条件 |
|---|---|---|---|
| 1 | 站点 | 首页 `/`、`/api/stats`、`/api/cases?limit=1` 三项本机回环探测（与 deploy.sh 健康检查同口径） | 任一项非 200 / 契约不符 |
| 2 | 同步任务 | `sync_runs` 5 个来源（大陆/香港/美国/韩国/西班牙）各自最近一次运行 | failed/error；running 超 3h（疑似卡死）；定时来源（香港）超 26h 未运行；首次部署有宽限（记起点，超 26h 仍无记录才告警）。手动来源（大陆/美/韩/西）无记录不告警 |
| 3 | 数据量 | 5 张案件表行数对比上次快照 | 骤降 ≥10 条且 ≥2%；暴涨 ≥100 条且 ≥20%（双阈值同时满足） |

- **告警通道：ClodHost 邮件 API**（`/etc/clodhost/api-keys.env`，服务器环境自带，不引入跨项目耦合）。默认收件人 `scx@polofox.com`（维护者），`INSPECT_ALERT_EMAILS` 可改。
- **去重与恢复**：同一问题（稳定 key）12 小时内不重复发；持续未恢复超冷却会再提醒；问题消失发「已恢复」通知。恢复邮件发送失败时保持 open，下轮重试。
- **状态文件** `/var/lib/baobeihuijia-inspect/state.json`：上次快照、每日计数（保留 40 天）、告警冷却、站点可用性计数。`--dry-run` 与 `--simulate` 不写状态（避免测试污染）。
- **报告**：`--report` 输出周报（近 7 天：站点可用性、数据量对比、同步运行汇总、未解决告警），`--report --days 30` 即月报。
- **健壮性**：退出码 0/1/2；未捕获异常时尝试发「巡检脚本自身故障」邮件；`sync_runs` 缺表（迁移未应用）单独告警。
- 自测：`--self-test` 内置 35 项断言（判断逻辑、告警冷却/恢复流转、文案格式、参数解析），不访问网络与数据库。

### 3.3 定时：systemd timer

单元放 `deploy/systemd/`（与 `baobeihuijia-health.timer` 同风格，日志进 journald、`Persistent=true` 补跑）：

- `baobeihuijia-inspect.timer`：开机 10 分钟后首跑，此后每小时的 :07 与 :37（每 30 分钟）。
- `baobeihuijia-inspect-report.timer`：每周一 01:23 UTC（09:23 北京时间）。

### 3.4 环境变量（均可选）

| 变量 | 默认 | 说明 |
|---|---|---|
| `INSPECT_BASE_URL` | `http://127.0.0.1:3000` | 站点探测地址（本机回环） |
| `INSPECT_ALERT_EMAILS` | `scx@polofox.com` | 告警收件人（逗号分隔） |
| `INSPECT_STATE_DIR` | `/var/lib/baobeihuijia-inspect` | 状态目录 |
| `INSPECT_SYNC_STALE_HOURS` | `26` | 定时来源心跳阈值（小时） |
| `INSPECT_RUNNING_MAX_HOURS` | `3` | running 卡死阈值（小时） |
| `INSPECT_DROP_PCT` / `INSPECT_DROP_MIN` | `2` / `10` | 数据量骤降阈值（百分比/条数） |
| `INSPECT_SURGE_PCT` / `INSPECT_SURGE_MIN` | `20` / `100` | 数据量暴涨阈值 |
| `INSPECT_ALERT_COOLDOWN_HOURS` | `12` | 同一告警重复发送间隔 |

## 五、验收标准

1. 人为制造一次失败，告警可达（维护者收到邮件）。
2. 巡检覆盖：同步任务心跳与结果、站点 200、数据量异常。
3. 周报/月报摘要可输出。
4. 工程约束：lint / tsc / build 通过；记录失败不影响同步；不把任何凭据回显到日志。

## 七、已知但本次不改

- 告警只有单一收件人与单一渠道（邮件）；分级/升级策略如需要可后续加。
- 大陆爬虫 cron 自 2026-09-03 起停用，按「手动来源」纳入（无记录不告警）；若重新启用定时，把 `scripts/inspect.ts` 中该来源的 `scheduled` 改为 `true` 即可恢复超时告警。
- 巡检只做「可访问性与契约」检查，不做页面内容正确性（如裂图）检查。
- 月报未装独立 timer，用 `--report --days 30` 手动触发或后续加装。
- `sync_runs` 迁移按仓库惯例由部署时手动 `psql` 应用，未纳入自动化。
